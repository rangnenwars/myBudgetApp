My Budget — database design

Schema & relationships

What tables exist, how they relate, and the one real normalization gap the old local schema had — now implemented and running in Postgres.

Implemented — matches server/src/db/schema.ts, verified by 52 passing server tests

Entity relationships

Every table hangs off users with a cascading foreign key. categories is mostly a global lookup table, but a nullable user_id also lets it hold a user's own custom categories — referenced by transactions/budgets like any other lookup, and owned by users like any other per-account table, at the same time.

What actually changes from the local schema

Most tables carry over as-is, just properly typed. Two things are genuinely new.

categories becomes a real table

Today, category is a free-text string on every transaction, matched against a hardcoded list in constants/categories.ts — client-side only, nothing stops a typo from silently creating an orphan category. As a table with a foreign key, that becomes structurally impossible.

What doesn't change at all

utils/calculations.ts — every pure function (computeMonthSummary, simulateDebtPayoff, bucketForGroup, all 15 of them) operates on plain arrays already fetched from storage. Swapping the storage layer for Postgres over HTTP doesn't touch this module or its 47 tests — that separation is the entire point of how the app was already built.
