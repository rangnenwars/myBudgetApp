A

Layered architecture

The app is fully online-only now — every data call is an HTTP round trip to the Express server, which is the only thing that ever touches Postgres. This is the call chain from a tap in the UI down through the database and back.

Why this shape

  • Screens never do math directly — they fetch rows and hand them to calculations.ts, or call a data-layer function that already delegates internally (on the server, inside the route handler).
  • utils/database.ts exports the same function names the old local storage layer did, so screen call sites barely changed — mostly just adding await.
  • Every server route is scoped by req.userId, read from the verified JWT — never a client-supplied id. This closes the account-isolation gap flagged in the Pro roadmap doc properly, at the source of truth instead of an app-level convention.

The platform-split pattern still shows up twice

Storage's platform split is gone now that everything is one HTTP client — but anywhere web and native genuinely need different code, the app still uses a foo.ts / foo.web.ts pair with identical exports, and Metro resolves the right one per platform. No Platform.OS branching inside a shared file.

Why alert.ts exists

react-native-web's Alert export is a literal no-op — its entire source is static alert() {}. Every delete-confirmation and save dialog in the app was silently doing nothing on web (button callbacks included) until this was found during manual testing and replaced. Any new confirm/alert dialog must go through utils/alert, never Alert from react-native directly.

Server test suite — 128 tests, real Postgres, no mocking, coverage-enforced

server/src/__tests__/*.test.ts — Jest + Supertest against a live database (not mocked). One file per resource (auth, categories, transactions, loans, investments, goals, reports, netWorth, admin), a small app.test.ts for the health check and generic 404, plus e2e.test.ts, a full lifecycle test: register → logout → re-login → bulk-log a month of data across every resource type → verify server-computed budget class → verify reports/debt-payoff/net-worth/CSV export all reflect it → tier toggle → logout invalidates the refresh token but not the still-live access token. Every file also checks cross-user data isolation and unauthenticated (401) access. Full endpoint documentation lives in docs/API_REFERENCE.md; server/jest.config.js enforces a coverage floor over src/routes/, src/middleware/, and src/lib/ (80% branches, 90% functions/lines/statements), and a Husky pre-commit hook runs the full suite before every commit that touches server/.

Not covered by automated tests

Client data layer (utils/database.ts, utils/api.ts) — no automated tests; the axios interceptor's silent-refresh-on-401 logic is exercised indirectly by the server's token-rotation tests but not from the client side.

AuthContext — untested; would need React Testing Library plus a mocked api module.

Screens — no component tests. Verified by manual click-through in the browser against the live Docker stack instead.

D

Quality-check framework

What's wired up in package.json so this stays checkable as the app grows. The client and server each have their own independent gate — commands below are the client's; server/package.json has the same shape (npm run typecheck, npm test, npm run test:coverage, npm run quality).

CommandDoes
npm testRuns the Jest suite once
npm run test:watchRe-runs on file change, for active development
npm run test:coverageRuns with a coverage report
npm run typechecktsc --noEmit — no build artifacts, just error checking
npm run qualitytypecheck + coverage together — the single gate to run before any build

Client coverage thresholds are pinned to calculations.ts specifically (85% branches, 100% functions, 90% lines/statements). Server coverage thresholds are pinned to src/routes/, src/middleware/, and src/lib/ (80% branches, 90% functions/lines/statements — see docs/API_REFERENCE.md). Either npm run quality fails the moment new code ships without tests.

Enforced on every commit, not just when someone remembers to run it

A Husky pre-commit hook (.husky/pre-commit, installed automatically via the root package.json's prepare script) runs the client's npm run quality on every commit, and the server's too whenever the commit touches server/ — blocking the commit if either fails. There's no CI service behind this repo (no remote), so this local gate is what actually keeps "tested every time a change happens" true in practice, rather than a policy that only holds as long as someone remembers.

E

Bulk entry & bucketing

New since the first version of this doc: app/input-expenses.tsx lets you log a whole batch of categories at once, mirroring the source Excel's one-row-per-category layout, instead of adding transactions one at a time.

The Expense / Loan / Investment badge is derived, not stored

Picking a category on a row shows a live badge (Expense, Loan, or Investment) computed by bucketForGroup(category.group) — but that bucket is never written to the transaction. It's recomputed the same way, from the same category group, wherever it's needed: once for the row badge as you type, and again later when the Dashboard breakdown reads back all of this month's transactions. "Moving" a row between buckets is just picking a category from a different group — there's no separate override field to keep in sync.

Category groupBucket
Loans & EMIs, Credit cardsLoan
Investments & savingsInvestment
Everything else (Household, Food, Transport, …)Expense

This same bucketForGroup call powers the Dashboard's "This month's breakdown" card — it re-derives the three totals from getCategoryBreakdown() on every focus, rather than reading a stored bucket.
